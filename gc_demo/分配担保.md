# 定义
## -XX:+UseSerialGC
JVM参数配置：  
-Xms20M -Xmx20M -Xmn10M -XX:+PrintGCDetails -XX:SurvivorRatio=8 -XX:+UseSerialGC  

1. 现在是尝试分配三个2MB的对象和一个4MB的对象，通过JVM参数 -Xms20M、-Xmx20M、-Xmn10M 把Java堆大小设置为20MB，不可扩展。  
2. 其中10M分配给新生代，另外10M分配给老生代。   
3. 然后通过-XX：SurvivorRatio=8来分配新生代各区的比例，设置为8，表示eden与一个survivor区的空间比例为8:1。  
4. 通过GC日志我们发现在分配allocation4的时候，发生了一次Minor GC，让新生代从7836K变为了472K，但是你发现整个堆的占用并没有多少变化。这是因为前面三个2MB的对象都还存活着，所以回收器并没有找到可回收的对象。但为什么会出现这次GC呢？
5. 如果你算一笔账就知道了，前面三个对象2MB+2MB+2MB=6MB。
虚拟机分配内存优先会分配到新生代的eden space，新生代可用内存一共只有9216KB，现在新生代已经被用去了6MB，还剩下9216KB-6144KB=3072KB，然而第四个对象是4MB，显然在新生代已经装不下了。
6. 于是发生了一次Minor GC！
而且本次GC期间，虚拟机发现eden space的三个对象（6MB）又无法全部放入Survivor空间(Survivor可用内存只有1MB)。  
这时候该怎么办呢？第四个对象还要不要分配呢？  
此时，JVM就启动了内存分配的担保机制，把这6MB的三个对象直接转移到了老年代。  
此时就把新生代的空间腾出来了，然后把第四个对象（4MB）放入了Eden区中，所以你看到的结果是4096/8192=0.5，也就是约50%：  
7. 担保后，之前在新生代的三个对象转移到了老生代

**新对象想进入eden区->  
eden区空间不足->  
触发Minor GC->  
如果Minor GC后空间仍然不足(是之前存在的对象放入S区发现放不了)->  
则触发担保机制，将对象（之前存在的对象）直接转移到老年代->  
老年代空间不足->  
触发Full GC-如果Full GC后空间仍然不足->  
则抛出OutOfMemoryError**


## -XX:+UseParallelGC
在GC前还会进行一次判断，如果要分配的内存>=Eden区大小的一半，那么会直接把要分配的内存放入老年代中。否则才会进入担保机制。
