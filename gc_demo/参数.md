### HotSpot参数分类
- 标准： - 开头，所有的HotSpot都支持
- 非标准：-X 开头，特定版本HotSpot支持特定命令
- 不稳定：-XX 开头，下个版本可能取消

### HotSpot参数说明

#### java -XX:+PrintCommandLineFlags
  
1. 作用是把所有生效的 VM 参数打印出来

```text
-XX:InitialHeapSize=533289216 -XX:MaxHeapSize=8532627456 -XX:+PrintCommandLineFlags -XX:+UseCompressedClassPointers -XX:+UseCompressedOops -XX:-UseLargePagesIndividualAllocation -XX:+UseParallelGC 

-XX:InitialHeapSize=533289216
初始堆大小 = 533,289,216 字节 ≈ 508 MB
JVM 启动时分配给堆的初始内存

-XX:MaxHeapSize=8532627456
最大堆大小 = 8,532,627,456 字节 ≈ 8 GB
堆能扩展到的上限（通常是物理内存的 1/4）

-XX:+PrintCommandLineFlags
就是自己配的那个参数，作用是把所有生效的 VM 参数打印出来

-XX:+UseCompressedClassPointers
开启类指针压缩
在 64 位 JVM 上，用 32 位指针存储类元数据指针，节省内存（可省约 30%）

-XX:+UseCompressedOops
开启普通对象指针压缩
同样在 64 位 JVM 上，将对象引用从 64 位压缩为 32 位，节省堆内存
上面两个参数是 Java 8 的默认优化，堆大小在 ~32GB 以下时自动开启

-XX:-UseLargePagesIndividualAllocation
关闭大页内存的单独分配
大页（Large Pages）是一种操作系统级别的内存管理方式，这里禁用了对大页的逐块分配

-XX:+UseParallelGC
使用 Parallel 垃圾收集器（吞吐量优先）
这是 Java 8 的默认 GC 策略
新生代和老年代都使用并行收集（多线程），适合后台计算类任务
```

#### java -Xmn10M -Xms40M -Xmx60M -XX:+PrintCommandLineFlags -XX:+PrintGC -XX:+PrintGCDetails -XX:+PrintGCTimeStamps -XX:+PrintGCCause

8. 说明
   - 0.051:：时间戳。表示 JVM 启动后第 0.051 秒发生的 GC。
   - [GC (Allocation Failure) ...]：
     - GC：代表 Minor GC（新生代垃圾回收）。如果是 Full GC 则是整个堆（包括老年代）的回收。
     - Allocation Failure：GC 触发原因。说明新生代空间不足，无法为新对象分配内存。
   - [PSYoungGen: 7290K->992K(9216K)]：新生代（Parallel Scavenge）的回收情况。
     - 7290K->992K：回收前新生代占用 7290K，回收后降为 992K（说明大部分年轻对象死掉了，回收效果很好）。
     - (9216K)：新生代当前的总容量（约 9MB）。
   - 7290K->6120K(39936K)：整个堆的回收情况。
     - 7290K->6120K：整个堆在回收前占用 7290K，回收后占用 6120K。
     - (39936K)：当前堆的总容量（约 39MB）。
   - 0.0012463 secs：本次 GC 造成的停顿时间（约 1.2 毫秒）。
   - [Times: user=... sys=... real=...]：CPU 耗时统计（real 是真实流逝时间，与上面的停顿时间一致）。

调优前的基础概念：
1. 吞吐量：用户代码时间 /（用户代码执行时间 + 垃圾回收时间）
2. 响应时间：STW越短，响应时间越好
所谓调优，首先确定，追求啥？吞吐量优先，还是响应时间优先？还是在满足一定的响应时间的情况下，要求达到多大的吞吐量...

问题：
科学计算，吞吐量。数据挖掘，thrput。吞吐量优先的一般：（PS + PO） 
响应时间：网站 GUI API （1.8 G1）

什么是调优？
1. 根据需求进行JVM规划和预调优
2. 优化运行JVM运行环境（慢，卡顿）
3. 解决JVM运行过程中出现的各种问题(OOM)
调优，从规划开始
- 调优，从业务场景开始，没有业务场景的调优都是耍流氓
- 无监控（压力测试，能看到结果），不调优
- 步骤：
  1. 熟悉业务场景（没有最好的垃圾回收器，只有最合适的垃圾回收器）
  响应时间、停顿时间 [CMS G1 ZGC] （需要给用户作响应）
  吞吐量 = 用户时间 /( 用户时间 + GC时间) [PS]
  2. 选择回收器组合
  3. 计算内存需求（经验值 1.5G 16G）
  4. 选定CPU（越高越好）
  5. 设定年代大小、升级年龄
  6. 设定日志参数
   - -Xloggc:/opt/xxx/logs/xxx-xxx-gc-%t.log -XX:+UseGCLogFileRotation -XX:NumberOfGCLogFiles=5 -XX:GCLogFileSize=20M -XX:+PrintGCDetails -XX:+PrintGCDateStamps -XX:+PrintGCCause
        - -Xloggc:/opt/xxx/logs/xxx-xxx-gc-%t.log
          指定 GC 日志的输出路径和文件名，同时隐含开启了 -XX:+PrintGC 和 -XX:+PrintGCTimeStamps（即使用户没写也会生效）。
        - /opt/xxx/logs/：日志目录
        - %t：占位符，会被替换成 JVM 启动时的第一个时间戳（形如 2026-10-17_09-30-15）
        - 最终文件名类似：xxx-xxx-gc-2026-10-17_09-30-15.log
        - -XX:+PrintGCDetails
          打印详细的 GC 信息：回收前后各分区的内存变化、耗时、停顿时间等（就是你之前看到的那种 PSYoungGen: 7290K->992K(9216K) 格式）
        - -XX:+PrintGCDateStamps
          在每条日志前打印人类可读的日期时间，例如 2026-10-17T09:30:15.051+0800:。
        - -XX:+UseGCLogFileRotation
          开启 GC 日志自动滚动（类似 logback 的 rolling）。不开的话，日志会无限增长，直到把磁盘写满。
        - -XX:NumberOfGCLogFiles=5：最多保留 5 个滚动文件。
        - -XX:GCLogFileSize=20M ：单个日志文件达到 20MB 时切下一个新文件。
  - 或者每天产生一个日志文件
  7. 观察日志情况
